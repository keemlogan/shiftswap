8. Conclusion

This report has described ShiftSwap, a web application that replaces the telephone-and-spreadsheet handling of substitute shifts in a small part-time workplace. This chapter assesses the result against the objectives of Chapter 1, summarises the size of the system, states its limitations, proposes future work, and records what the team learned about requirements engineering and vibe coding.

8.3 Limitations

The system has the following limitations. Most follow from the decision to build a demonstration system on static hosting and a free hosted database without accounts (design decisions D1 and D13); they are listed so that the reader can judge what the results above do and do not show.

  • No authentication; identity is not enforced. Sign-in is the choice of a demo account without a password (FR-20). In the shared mode anyone who opens the application can act as any person, including the owner, and change the shared store. The row triggers enforce the state rules, the server time and the limits, but not who makes a change, and every row of the store, including phone numbers and wages, can be read with the publishable key. The role restriction and the privacy rule NFR-11 therefore protect against accidental, not deliberate, disclosure, and the demonstration contains only fictional data.
  • Whole-store replica. Each client loads a snapshot of the entire store when it starts and again after every change made elsewhere, and every commit is checked against one revision number per store. Two unrelated changes made at the same moment therefore also conflict, and the second is re-run; after three conflicts the user is asked to try again. This suits a store with a few people and a demonstration of a few hundred rows, but the cost of a reload grows with the history, and the store is capped at 20,000 rows. Changes by others are seen by polling every ten seconds, not pushed.
  • Rate limits count only successful commits. The limits of 60 changes a minute and 3,000 a day per store are counted in the same transaction as the change, so a refused or failed attempt is not counted. The limits bound the data that can be written, not the number of requests that reach the server.
  • Free plan and keep-alive. On the free plan, a project that shows low activity over seven days is paused until it is resumed manually [16]. The six-hourly keep-alive workflow prevents this, but GitHub disables scheduled workflows in a public repository after 60 days without repository activity [17]. If the database is paused or unreachable, the application offers only the local demonstration mode until the team resumes the project.
  • Browser storage in the local mode. In the local demonstration mode the data are kept in localStorage, which the user or the browser can clear and which is limited to a few megabytes per site. Neither mode provides backups or export.
  • Clock-driven work needs an open client. In the shared mode requests expire and the monthly payroll draft is prepared by the server time, but the work is performed and saved by whichever client has the application open; if nobody opens it, nothing expires until someone does. In the local mode expiry follows the demo clock and is triggered by navigation.
  • Legal scope. The pay rules cover the minimum wage, the weekly holiday allowance, overtime and night premiums, the premium for part-time hours beyond the contract and the probation reduction. The part-time worker's consent to extra hours is not recorded, and the 12-hour limit of BR-15 is a warning to the owner, not a block. Holiday-work premium, annual leave, severance pay, tax and social insurance are outside the scope, and the four-week average of the 15-hour rule is simplified to the weekly contractual value (BR-06). The treatment of a handed-over shift is a setting because the law does not decide it. The system applies these rules consistently but is not legal advice.
  • Evaluation. The requirements came from one reference store, and the interviews and prototype sessions were used to confirm requirements, not to measure them. No store has used the system in operation, so the effect on the number of contacts per request (problem P1) has not been measured.
  • Test and reproduction gaps. The browser checks of NFR-06 are recorded only for Chrome, and the shared mode was checked with two headless browsers on one computer rather than with several phones on mobile networks. The reproducibility of each prompt version rests on one run (Section 5.6.2), and a generative assistant does not produce the same code twice.

8.4 Future Work

Earlier versions of this section named a shared database as the most important extension; iteration 8 implemented it (Section 5.4.8). The layered design made this a change of the data-access layer: the rules and the services run unchanged on a replica, and a gateway saves their changes in the shared database. The following would be the next increments:

  1. authentication with real accounts and row ownership on the server, so that the owner and each worker can change only their own data, and NFR-11 is enforced by the database rather than by the interface;
  2. updates pushed by the database to the open clients instead of polling every ten seconds, and loading only the changed rows instead of the whole store;
  3. push or messenger notifications for new requests, in addition to the in-app inbox;
  4. expiry and the monthly payroll draft driven by a scheduled job on the server instead of an open client;
  5. a field trial in the reference store, measuring the number of contacts per request and the time to fill a shift before and after, which is the measurement G1 ultimately stands for;
  6. recorded checks in Edge, Safari and Firefox and on real phones, and repeated reproduction runs of the final prompt;
  7. recording the part-time worker's consent to extra hours, export of confirmed payroll as a payslip, and several stores per owner, for which the shared database already separates the data by store.

8.5 Lessons Learned

The specification is the program's real source. In vibe coding, the AI coding assistant writes the code, and the quality of the code is bounded by the precision of what it is told. The team's most useful decision was to keep one specification file with every identifier, rule, state and seed value, and to change it before changing anything else. When a question arose — who is notified when a request is cancelled, whether a week in progress can be "perfect" — the answer was written into the specification, and the next generated version had to follow it. This is requirements management as the lecture describes it [7]: individual requirements are tracked, their dependencies are recorded, and changes go through a defined procedure. Without it, three documents, a set of UML diagrams and the code would have drifted apart within a week.

Generation exposes incompleteness. The lecture states that in practice a complete and consistent requirements document is impossible [7]. The build iterations confirmed this concretely: in iteration 1 the AI coding assistant met more than twenty points where the specification was silent or ambiguous and had to choose. Recording each choice and turning it into specification text (Section 6.9) worked as a requirements review performed by the implementer. The lesson for vibe coding is that the log of the generator's decisions is as valuable as the code, because it shows where the requirements were weaker than the team believed.

Testable rules make generated code checkable. Code produced by an AI coding assistant cannot be trusted because it looks right. Placing every business rule in a pure function and deriving tests from the rules at their boundary values (14.99 and 15 hours, four and five employees, the last day of probation) gave the team an objective check that did not depend on reading every line. When the specification changed, the tests changed first. This is the test-first practice of extreme programming [6] applied to a prompt instead of to hand-written code.

Models find what text hides. The state diagram of the substitute request made it easy to see that every open state needs an exit by time and by the requester, and the traceability matrix showed which requirements had no test. The demonstration walkthrough S7 was added because the team noticed that no scenario ever changed a worker's eligibility, so the highlight required by FR-11 had never been exercised. Chapter 2 of the lecture presents models as a means of discussion, documentation and implementation [6]; in this project they served mostly as a means of checking.

The incremental model suited the course. Placing all Must use cases in the first increment meant that the substitute workflow, the core of the project, was working and testable before the payroll rules were built, as the lecture's description of the incremental model promises [6]. The weakness the lecture warns of, degradation of structure as increments are added, was contained by fixing the layered architecture before the first increment; the second increment added functions to the existing layers and did not change their boundaries.

Names are not interfaces. Reproduction run 1 rebuilt a system that behaved as specified but passed only 13 of the team's 25 rule tests, because the prompt fixed the names of functions but not their signatures and return shapes. Supplying the acceptance tests as part of the input closed this gap: run 2 passed all 77 supplied tests unchanged, and runs 3 and 4, after the requirements changes of iterations 6 and 7, all 84 and all 89. For vibe coding, the lesson is that the executable tests belong to the contract, not only to the verification of one build.

Retire requirements; do not reuse their numbers. The change request of iteration 6 removed a use case, a functional requirement and a table after the product owner had used the running system. Because the traceability links were part of the specification, the impact analysis was a search for identifiers, and the change reached the code, the tests and this report within one iteration. Keeping the retired numbers FR-03 and UC-02 unused preserved the meaning of every earlier record that mentions them.

A shared server is part of the contract. Iteration 8 showed that the rules that matter most once several devices share one store — who may change which row, and which of two simultaneous acceptances wins — cannot be left to generated client code, because any browser can be modified. The team therefore wrote the server side once and supplied it with the prompt, together with a test file for the protocol between client and server, and let the unchanged services run on a replica; as a result, the 89 tests of iteration 7 passed unchanged in the new architecture.

Documents need the same discipline as code. Because code can be regenerated in hours, the documents became the slower part of the project, and they drifted more easily than the code. Several corrections in this report — the recipients of a cancelled request, the storage of the minimum-wage acknowledgement, the course calendar — were found by checking documents against the specification and the tests. A team using vibe coding should plan as much time for keeping the requirements, models and report consistent as for generating the software.

ShiftSwap shows that a small team can take a real problem from a part-time job through problem definition, requirements, design, implementation by vibe coding and testing within one semester, and arrive at a system whose behaviour is specified, traceable and tested. What remains is to enforce identity on the shared server and to measure the system's effect in a real store.
