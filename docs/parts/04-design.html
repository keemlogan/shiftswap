4. Design Specification

This chapter describes how ShiftSwap provides the functions specified in Chapter 3. The lecture divides design into architectural design (the structure of the system), interface design (the interfaces between its parts) and detailed design (the algorithms of the individual parts) [6]. Section 4.1 presents the architecture with its two data modes and Section 4.2 the deployment. Section 4.3 records the main design decisions and the alternatives that were rejected. Sections 4.4 and 4.5 give the static design: the class model and the database. Sections 4.6 and 4.7 give the dynamic design: sequence diagrams for the four central use cases and state machines for the three entities with a life cycle. Section 4.8 specifies the algorithms of the business rules, and Section 4.9 the design of the user interface.

The design is described as it is implemented. Every module, function and table named in this chapter — including the objects of the shared database in db/app-shared.sql — exists under the same name in the repository, and the functions are the ones called by the tests of Chapter 6. Where a UML diagram shows an operation at a more abstract level than the code, the text gives the name of the implementing function. The parts added in iteration 8 — the shared-data gateway app/core/shared.js, the configuration app/config.js and the shared database — are described in the same way.

4.1 Architecture

4.1.1 Layers

ShiftSwap has a layered architecture with two data modes, introduced in iteration 8 (Section 3.11.6). In the shared mode, the default, the owner and the workers use one store in a shared database on Supabase, a hosted PostgreSQL service with a free plan [16]; everyone who opens the application sees and changes the same data. In the local demonstration mode, which keeps the behaviour of iterations 1 to 7, the same tables exist only in the user's browser. In both modes all application code runs in the browser, and a static web host delivers the files. In the shared mode the browser also calls three functions of the shared database through its REST interface, using only the publishable key of the project; the system has no application server of its own (NFR-06). The table below lists the seven parts of the architecture. Each layer may call only the layers below it, and the domain-rule layer calls nothing at all. The application services and the rules are the same code in both modes.

4.1.2 Transactions and persistence

The data-access module keeps one SQLite database in memory, created by sql.js [9]. Every service command is wrapped in tx(fn), which executes BEGIN, runs the function, and then executes COMMIT; if the function throws, it executes ROLLBACK and passes the error on. A nested call of tx() joins the outer transaction instead of opening a second one, so that decideRequest can call recomputeWeek and both changes commit or roll back together. In the local demonstration mode, the whole database is exported as bytes after a successful commit, encoded in base64 and saved to localStorage under the key shiftswap.db.v2 (v1 until iteration 7, when the seed gained the work history). On start, openDatabase loads the saved copy if one exists and has the current schema; otherwise it creates the schema, inserts the seed data and saves it (NFR-05).

In the shared mode the in-memory database is a working copy of one store of the shared database and is not saved in the browser. On start, the gateway calls app_snapshot(store), which returns every row of the store, the revision number of the store and the server time, and loadTables builds the working copy from these rows with the schema of spec §8. A command runs the unchanged service function inside tx() on the working copy. The gateway then compares the tables with their state at the last synchronisation (dumpTables) and sends the changed rows — inserts, updates and deletes by primary key — together with the revision on which they were computed to app_commit(store, base_rev, changes). The server applies this change set in one transaction: it locks the store row with SELECT … FOR UPDATE, refuses the change set with STALE if its base revision is no longer the current one, checks the rate limits and sizes, applies the deletes, updates and inserts, lets the row triggers check the rules it can decide itself, checks the deferred foreign-key and uniqueness constraints (SET CONSTRAINTS ALL IMMEDIATE) and increments the revision. Any violation rolls back the whole change set (Section 4.5.2). On STALE the gateway reloads the snapshot and runs the same command again on the current data, at most three times; when a rule of the server refuses the change, it reloads and runs the command once more, so that the user sees the service's own message rather than an error of the server (spec §9).

Because a failing service throws a ServiceError inside tx(), a rejected operation never leaves a partial change behind. This is the mechanism behind NFR-04: the acceptance of a request re-reads the request inside the transaction and, if it is no longer REQUESTED, throws before anything is written. In the shared mode a command that fails before it changes anything sends nothing to the server, and the server's row lock and revision check extend the guarantee to acceptances made in different browsers (Section 4.6.2).

4.1.3 The clock and the System Clock actor

All time-dependent behaviour — whether a shift is in the future, whether a deadline has passed, the default deadline, the time stamps of notifications — uses now() from clock.js. In the shared mode now() returns the server time in Korea Standard Time: every snapshot and every commit returns the time of the server, and the clock keeps its difference from the clock of the device, so that deadlines are judged by the same time in every browser. This clock cannot be set. In the local demonstration mode now() returns the demo clock, which starts at 2026-09-28 09:00 (the Monday of the seed data), is stored under shiftswap.clock.v1, and can be set or advanced by one hour or one day in Demo tools. The System Clock actor A3 of the use-case model is realised by the router: before rendering any screen, main.js calls expireOverdue() and then, since iteration 7, prepareMonthlyPayroll(). Both therefore run on start, on every route change and, in the local mode, after every change of the demo clock: a request whose deadline has passed is expired before any user can see or act on it, and on or after the first day of a month the previous month's payroll draft exists before the owner opens Home (UC-14). In the shared mode these duties are performed by whichever browser has the application open. Their changes are committed in the background like those of a command, and the server accepts an expiry only when the request is overdue by its own time (BR-12). If the server refuses such a change, the working copy is reloaded and the duties pause for one minute.

4.2 Deployment

The deployment diagram above shows the nodes of the deployed system. GitHub Pages serves the static files of the repository over HTTPS [13]; it runs no application code. The browser on the user's device downloads index.html, the JavaScript modules, the style sheet and the two sql.js files and runs all application code. In the local demonstration mode nothing else is contacted. In the shared mode the browser also connects over HTTPS to the Supabase project shiftswap, whose PostgreSQL database holds the shared store (Section 4.5.2); it reads the store and calls the three database functions through the REST interface of the project with the publishable key, which permits nothing else. The sql.js files (sql-wasm.js and sql-wasm.wasm, version 1.14.2) are copied into app/vendor/, so the application does not depend on a content-delivery network at run time. All URLs in the application are relative, so the same files work under the sub-path /shiftswap/app/ of the deployed site and under any local static server. Chapter 7 describes the deployment procedure.

A third element of the deployment is the scheduled workflow .github/workflows/supabase-keepalive.yml of the repository (NFR-16). On the free plan of Supabase, a project that shows low activity over seven days is paused, and it stays paused until it is resumed manually from the Supabase dashboard [16]. The workflow therefore sends a read query to the project every six hours (cron 23 */6 * * *, and on demand); the service documentation states that a few user requests to the database each day are typically enough to keep a project from being paused [16]. The query reads the version heads of the project hub (Section 7.1.5), which are stored in the same project, so it keeps the database of the application active as well. GitHub disables scheduled workflows in a public repository after 60 days without repository activity [17]; the team therefore also checks the public URL every week until grading ends and before every submission, as planned in the proposal.

If the browser refuses storage (for example in some private-browsing modes), main.js falls back to an in-memory store, and the application still works for the length of the visit.

The operations are queued and performed one after another, so that a command, the saving of System Clock work, a poll and a reset never overlap. The gateway passes these to the screens as ServiceError codes (D10), for example SHARED_BUSY when a change set is still stale after three re-runs. The module app/config.js supplies the URL of the Supabase project, the publishable key and the slug of the demo store, dalbit; if the URL or the key is empty, the application starts in the local demonstration mode.

4.5 Database Design

The database has eleven tables, nearly three times the minimum of four set by the course; the twelfth table of earlier versions, Availability, was removed in iteration 6 (Section 3.11.4). The schema is the SQL of spec §8, executed verbatim by db.js. All identifiers are English (NFR-09). SQLite has few column types; the schema uses INTEGER for keys, counts, flags (0/1) and amounts in won, REAL for hours, and TEXT for dates (YYYY-MM-DD), times (HH:MM), datetimes (YYYY-MM-DDTHH:MM) and enumerations, which are restricted by CHECK constraints. Storing dates and times as ISO text has a practical advantage: they sort and compare correctly as strings, so the services can compare a deadline with now() directly. Money is never stored as a floating-point number. Since iteration 8 the same eleven tables also exist in the shared database, where they are held in PostgreSQL with a store column and composite keys; Section 4.5.2 gives this physical mapping.

The tables fall into four groups: master data (Workplace, Worker, FixedSchedule, MinimumWage), transactions (Shift, SubRequest, SubRequestTarget, Attendance), derived results (WeeklySummary, Payroll) and communication (Notification). 4.5.1 Normalisation and integrity

The master and transaction tables are in third normal form: every non-key column depends on the whole primary key and on nothing else. There are no repeating groups — a worker's several fixed shifts are rows of their own table rather than columns of Worker — and names of workers are stored only in Worker and joined where needed. Two tables deliberately hold derived data. WeeklySummary is a cache of values that can be recomputed from Shift, Attendance, FixedSchedule and Workplace; it is kept consistent by recomputing the affected rows inside the transaction that changes their inputs (approval, attendance confirmation, marking absent, payroll generation, and opening the weekly summary screen). Payroll is a snapshot: once CONFIRMED, it must keep the amounts that were paid even if shifts change afterwards (TC-115), which is why it cannot be a view.

Integrity rules are enforced at two levels. The schema enforces what SQL can express locally: primary keys, NOT NULL, the permitted values of every status column, one attendance record per shift (Attendance.shiftId UNIQUE), one summary per worker and week, and one payroll row per worker and month. The services enforce the rules that involve several rows or the clock: no overlapping fixed shifts or shifts of one worker (FR-02, FR-05), at most one open request per shift (BR-03), first acceptance wins (BR-02), and no deletion of a shift that has a request or attendance record (FR-05). Foreign keys are declared with REFERENCES for documentation and for the ER diagram; the services never delete a row that is still referenced. In the shared mode a third level is added: the shared database enforces its foreign keys, allows at most one open request per shift with an index, and re-checks the life cycles and time rules with row triggers (Section 4.5.2), so that a modified client cannot bypass the rules that the server can decide itself.

The three public functions form the whole interface of the shared database. app_snapshot(store) is a read-only SQL function that returns the revision, the server time and every row of the store, grouped by the table names of the working copy. app_commit(store, base_rev, changes) and app_reset(store) are SECURITY DEFINER functions with an empty search_path, so that they write with the rights of their owner and cannot be redirected to objects of the caller. app_commit refuses a change set larger than 256 kB or 2,000 row operations, locks the row of the store, refuses a stale base revision (STALE), checks and updates the counters of app_store_gate (60 change sets a minute, 3,000 a day), and applies the deletes, the updates and then the inserts. A delete is accepted only for FixedSchedule, Shift, WeeklySummary, Payroll and MinimumWage rows; requests, targets, attendance records and notifications are never deleted by a client. An update or delete that finds no row is refused as a conflict. After the inserts the function refuses a store of more than 20,000 rows (STORE_FULL), checks the deferred constraints and increments the revision. Because all of this runs in one transaction, a refused change set also leaves the rate-limit counters unchanged.

The row triggers re-check what the server can decide without knowing the user. The trigger on SubRequest permits only the transitions of the state machine of spec §7 (Section 4.7.1): a new request must be REQUESTED, or FAILED when it has no candidates, and must be made by the current worker of a SCHEDULED shift, with a deadline between the server time and the shift start; an acceptance must come from one of the request's targets and, like an approval, must happen before the deadline and the shift start by server time; an expiry is accepted only when the request is overdue by server time (BR-12); the shift, the requester, the deadline and the reason never change, and a request is never deleted. The other triggers keep a target's worker and request fixed and an answered target unchanged, permit only the shift transitions of Section 4.7.2 and keep the original worker of a shift (BR-04), keep a confirmed attendance record unchanged, make CONFIRMED payroll rows read-only and refuse a confirmation while a minimum-wage warning is unacknowledged (BR-09), allow only the read time of a notification to change, and allow the workplace of a store to be updated but not created or deleted. The creation time of a new request or notification must lie within ten minutes of the server time.

app_reset(store) is limited to one reset a minute and 50 a day per store. It replaces the rows of the store with the seed template app_seed_template(), whose 353 rows are generated from the seed code of spec §10 by tools/seed-sql.mjs; a unit test checks that the template is up to date (TC-16A). All dates of the template are moved by the smallest number of whole weeks that leaves the seed request of Lee Seoyeon open for at least six hours, so weekdays, times and the walkthroughs of spec §10 remain valid. Shifts that have not ended by the server time become SCHEDULED without attendance, and creation times later than the server time are set to it. The template contains no Payroll rows, because calendar months do not move with whole weeks; the first client that opens a store without Payroll rows completes the payroll history with the same code as the local seed (completeSharedSeed) and saves it like any other System Clock work.

4.6 Dynamic Design: Sequence Diagrams

The lecture describes a sequence diagram as the interactions that take place during a particular use case, with the objects along the top and function calls as horizontal arrows [6]. Five sequence diagrams — SD-1, SD-2, SD-3a, SD-3b and SD-4 — cover the use cases with the most interaction. For each sequence diagram, the numbered steps name the functions of the implementation.

4.6.1 SD-1 Request substitute (UC-04)

  1. The worker starts the request flow. Its first step lists the worker's requestable shifts with listRequestableShifts(workerId), and its second step fills the deadline with defaultDeadline(shift), the earlier of now + 24 h and the shift start.
  2. When the worker sends the request from the review step, the screen calls createSubRequest({shiftId, requesterId, reason, deadline}), which opens a transaction with tx().
  3. The service reads the shift and counts the open requests on it, then calls validateRequest with the current time from now(). If the result contains an error code, it throws a ServiceError with that code; the transaction rolls back and the screen shows the translated message (the "request invalid" branch).
  4. Otherwise the service inserts the SubRequest with status REQUESTED.
  5. For every worker, the service reads that worker's shifts on the date and calls isEligibleCandidate (the loop of the diagram; the included use case Find eligible candidates).
  6. For each eligible candidate it inserts a SubRequestTarget with response PENDING and a REQUEST_RECEIVED notification. If there is none, hasNoTaker holds for the empty list of responses: the service sets the request to FAILED and sends REQUEST_FAILED to the requester and the owner (BR-13).
  7. The transaction commits. In the local mode the database is saved to localStorage; in the shared mode the gateway sends the created rows as one change set to app_commit, whose trigger checks the status, the deadline and the creation time against the server time, and the screen waits for this save. The service returns the request id, its status (REQUESTED or FAILED) and the list of candidates, which the screen shows.

4.6.2 SD-2 Accept request with concurrent second acceptance (UC-05)

  1. Both candidates see the same pending request in their own browsers, built for their screens by the service queries (listNotifications, and on the Home screen getWorkerHome), with Accept and Can't. Both working copies are at revision r of the store.
  2. Candidate 1 selects Accept; the screen passes respondToRequest(requestId, workerId, 'ACCEPTED') to the gateway (ctx.run), which runs it on the working copy inside a transaction.
  3. Inside the transaction the service reads the request and the candidate's target. Both are REQUESTED and PENDING, so the service executes the conditional update UPDATE SubRequest SET status = 'ACCEPTED', acceptorId = ? WHERE id = ? AND status = 'REQUESTED'. The database reports one changed row.
  4. The service sets the candidate's target to ACCEPTED, sets every other PENDING target to CLOSED with a TARGET_CLOSED notification, and sends REQUEST_ACCEPTED to the requester and the owner. The transaction commits on the working copy, and the gateway sends the changed rows with base revision r to app_commit. The server locks the store row, finds revision r current, lets the trigger check the transition REQUESTED → ACCEPTED, the target and the deadline and shift start against the server time, applies the rows and returns revision r + 1.
  5. Candidate 2 selects Accept at nearly the same moment. On the working copy of the second browser the request is still REQUESTED, so the same steps succeed locally, and the gateway sends its change set with base revision r. If it arrives while the first change set is being applied, the server waits for the row lock; in either case it then finds revision r + 1 and refuses the change set with STALE, and nothing of it is written.
  6. The gateway of candidate 2 reloads the snapshot and runs respondToRequest again on the current data. The first read now finds the request ACCEPTED with another acceptor, and the service throws ServiceError('ALREADY_TAKEN') with the acceptor's name, which the screen shows as "already taken by Choi Minho". Because the re-run changed nothing, nothing more is sent. Within one working copy — and in the local mode, where both accounts use the same database — the conditional update alone decides: an update that finds the status no longer REQUESTED changes zero rows, and the service refuses with the same code.
  7. The last part of the diagram shows an answer of can't from the last candidate whose target is still PENDING (BR-13, FR-22). Inside the transaction the service sets the target to DECLINED and reads the responses of all targets of the request again. If every target is now DECLINED, the service sets the request to FAILED with a conditional update on status = 'REQUESTED' and sends REQUEST_FAILED to the requester and the owner; otherwise the request stays REQUESTED and no one is notified. In the shared mode this change set also goes through app_commit, so two answers of can't given at the same time are serialised by the revision check, and the second is recomputed on data that already contain the first.

SQLite has no SELECT … FOR UPDATE, so the service does not lock the row before reading it. Instead, the condition status = 'REQUESTED' is part of the update itself, and the check of the changed-row count happens in the same transaction; only one of two competing updates can affect the row. This is sufficient within one database. Across browsers, where each acceptance is first computed on a separate working copy, the guarantee of NFR-04 comes from the server: app_commit applies change sets one at a time under the row lock of the store and only to the revision on which they were computed, so of two change sets computed on the same revision only the first is applied (D6, D13). In addition, the trigger permits ACCEPTED only from REQUESTED, and at most one open request per shift is allowed by the partial unique index. The scenario was tested with the throwaway store of the REST test (Chapter 6) and with two headless browsers (tools/shared-check.mjs), in which one of two simultaneous acceptances succeeded and the other was told that the request had already been taken.

4.6.3 SD-3 Approve substitution with weekly recomputation (UC-06)

  3. It builds the "after" list by removing the requested shift and adding it back reassigned to the acceptor, and calls computeWeeklySummary again.

  5. If overtime.warn is set, the decision card and the details show that the acceptor would work the given number of hours beyond contract, with the limit of 12 hours a week for part-time workers (Section 4.8.3).   1. The owner selects Approve; the screen calls decideRequest(requestId, 'APPROVED'), which opens a transaction and reads the request with its shift. If the request is not ACCEPTED (BR-04), the service throws NOT_ACCEPTED and the transaction rolls back.
  2. Otherwise it executes UPDATE Shift SET workerId = acceptor, originalWorkerId = COALESCE(originalWorkerId, shiftWorkerId), so the first owner of the shift is kept even after several swaps, and sets the request to APPROVED with the decision time.

4.6.4 SD-4 Generate monthly payroll (UC-09, UC-14)

  1. The draft is started in one of two ways, shown as alternatives at the top of the diagram.   2. The service looks up the minimum wage of the year with minimumWageFor and determines the weeks whose Sunday falls in the month. For each of these weeks it calls recomputeWeek (the included UC-08).
  3. It deletes the DRAFT rows of the month; CONFIRMED rows are kept and their workers are skipped.
  4. For each worker it reads the month's shifts that are not ABSENT. A WORKED shift with recorded times contributes its clock-in and clock-out; any other shift contributes its scheduled times and is marked estimated (BR-11). It reads the holiday hours of the month's weeks from WeeklySummary.

4.7.2 Shift

A shift is created as SCHEDULED by generateWeek or editShift. An approved substitution (decideRequest) changes its worker but not its status. 4.7.3 Payroll

4.8 Algorithm Design

This section specifies the algorithms of the business rules in pseudocode. The pseudocode was derived from rules.js and uses the same names; it omits type conversions and formatting. Times are handled on a minute axis of the shift's date: span(start, end) returns the start and end in minutes after midnight and adds 1,440 minutes to the end when the end is not later than the start, so that an overnight shift is one continuous interval.

4.8.1 Candidate selection (BR-01)

function isEligibleCandidate(worker, requesterId, shift, workerShifts):
    if not worker.active:                return false
    if worker.role ≠ WORKER:             return false   -- the owner is never a candidate
    if worker.id = requesterId:          return false
    for x in workerShifts:                         -- the worker's shifts on shift.workDate
        if x.workDate = shift.workDate and overlaps(x, shift):
            return false
    return true                                    -- no availability check since iteration 6

function hasNoTaker(responses):                    -- BR-13; responses of the request's targets
    return every r in responses is DECLINED        -- true for an empty list: no candidate at all

function overlaps(a, b):                           -- half-open intervals [start, end)
    (as, ae) := span(a); (bs, be) := span(b)
    return as < be and bs < ae

The service applies this function to every worker with role WORKER (createSubRequest). The owner is not in this set, and the order of the checks follows the activity diagram AD-2 in Section 3.9. With five workers and at most a few shifts per worker and day, the cost is negligible. The half-open comparison makes shifts that meet at a boundary, such as 10:00–16:00 and 16:00–22:00, non-overlapping (TC-011); this is why Kang Doyun, whose Sunday shift starts at 16:00, is asked in walkthrough S8 for Jung Hana's shift that ends at 16:00. hasNoTaker is evaluated after each answer of can't and once at creation, where an empty list of candidates makes it true, so both endings of BR-13 share one function.

4.8.2 Weekly summary and holiday allowance (BR-06, BR-07)

function computeWeeklySummary(W, contract, shifts, policy):
    -- shifts: the week's shifts whose current worker or original worker is W
    scheduled := 0; actual := 0; reasons := []
    if contract < 15: reasons.add(CONTRACT_BELOW_15)
    for s in shifts ordered by date and start:
        original := s.originalWorkerId if set, else s.workerId
        if s.workerId = W:
            scheduled += duration(s)
            if s.status = WORKED and s has clockIn/clockOut:
                actual += duration(s.clockIn, s.clockOut)
        if original ≠ W: continue                   -- a shift W took as substitute
        if s.workerId = W and s.status = ABSENT: reasons.add(ABSENT on s.workDate)
        if s.workerId ≠ W and policy = ABSENT:   reasons.add(GAVE_AWAY on s.workDate)
    perfect  := no reason other than CONTRACT_BELOW_15
    eligible := contract ≥ 15 and perfect
    hours    := round2(min(contract, 40) / 40 × 8) if eligible else 0
    return (contract, scheduled, actual, perfect, eligible, hours, reasons)

Three properties of the rule are visible in the pseudocode. A shift the worker took as a substitute adds to scheduled hours but is skipped for attendance (the continue), so an absence on someone else's shift does not cost the substitute his own allowance (TC-087). A SCHEDULED shift is never a reason, so a week in progress is a projection (TC-085). And the policy is consulted in exactly one place. Holiday pay is computed later, per week: floor(hours × hourlyWage), and the month sums the rounded weekly amounts (BR-07). For Choi Minho, contract = 16, so hours = round2(16 / 40 × 8) = 3.2 and pay = floor(3.2 × 10,320) = 33,024.

4.8.3 Premium hours and the part-time limit (BR-08, BR-15)

function premiumHours(shifts, regularEmployees, options):
    -- options (iteration 8): contractHours C, payroll month, context shifts
    if regularEmployees < 5: return (daily 0, weekly 0, night 0, partTime 0, total 0)
    byDay := map date → hours; night := 0
    for s in shifts:                                -- worked or scheduled intervals of the month
        (a, b) := span(s)
        byDay[s.workDate] += (b − a) / 60
        night += minutes of [a, b) inside 22:00–06:00 windows / 60
    daily := 0; byWeek := map monday → regular hours
    for (date, h) in byDay:
        extra := max(0, h − 8);  daily += extra
        byWeek[weekStartOf(date)] += h − extra      -- only hours not already counted as daily overtime
    weekly := Σ over weeks of max(0, regular − 40)
    partTime := 0
    if isPartTime(C):                               -- 0 < C < 40, rule (a)
        hoursOf := byDay + hours of context shifts on dates outside the month
        for date in hoursOf in chronological order:  -- rule (c): the first C hours of the ISO week are within contract
            before := hours of the week before date; upTo := before + hoursOf[date]
            if date is not in the month: continue    -- context only places the first C hours; never paid
            overContract := max(0, upTo − max(C, before))
            beyond[week] += max(0, overContract − max(0, byDay[date] − 8))   -- rule (d): not counted in (i)
        partTime := Σ over weeks of max(0, beyond[week] − weekly overtime of that week)   -- nor in (ii)
    return (daily, weekly, night, partTime, daily + weekly + night + partTime)

premiumPay := floor(total × hourlyWage × 0.5)

function partTimeLimitCheck(regularEmployees, C, S):   -- BR-15; S = scheduled hours of the week after the swap
    beyondContract := round2(max(0, S − C))
    return (beyondContract, warn = regularEmployees ≥ 5 and isPartTime(C) and beyondContract > 12)

The night windows are checked against three intervals on the minute axis, from 22:00 on the previous day to 06:00, from 22:00 to 06:00 of the next day, and the following night, which covers any shift of less than 24 hours. Weekly overtime is computed from the regular hours only, so an hour that already earned daily overtime is not counted again (TC-094). Because the function receives only the shifts of the payroll month, a week that spans two months contributes only its days inside the month, as BR-08 requires.

Iteration 8 added part (iv) of BR-08, the hours of a part-time worker beyond the weekly contractual hours, which earn a premium of at least 50 % in a workplace with five or more regular employees under the Fixed-term and Part-time Employees Act [15]. The Act does not fix how these hours are to be counted, so the algorithm implements system rules that are design decisions of this project, not statements of law (spec BR-08 (a)–(e)): (a) a worker whose contractual hours C, the sum of the current fixed schedule as in BR-06, satisfy 0 < C < 40 is part-time; (b) the test is weekly against C, not daily; (c) the hours of an ISO week are taken in chronological order, each shift on its work date, and every hour after the first C hours is beyond contract — in a monthly payroll the days of that week outside the month only determine where the first C hours end; (d) an hour that meets more than one of (i), (ii) and (iv) is counted once; and (e) night hours are added separately. Without the options argument the function returns exactly the result of iteration 7. For the walkthrough S10 of spec §10, Choi Minho (C = 16) works 29 hours in the week of 28 September in the order Tuesday 5, Wednesday 5, Thursday 5, Friday 8 and Saturday 6 hours; the contractual hours end one hour into Friday, so 13 hours are beyond contract and October's premium includes 13 × 10,320 × 0.5 = 67,080 won for them.

partTimeLimitCheck implements the warning of BR-15, which the approval preview computes for the acceptor with the scheduled hours S of the "after" summary (Section 4.6.3). The limit of 12 hours a week beyond contract is taken from the Act [15]; the comparison of the scheduled hours of the swap week with the fixed-schedule hours is again the system rule of BR-08 (a)–(c). Exactly 12 hours beyond contract gives no warning and 13 hours give one (TC-15x). The warning never blocks the approval, because the worker's consent and the owner's decision lie outside the system.

4.8.4 Probation reduction and minimum-wage check (BR-09, BR-10)

function probationApplies(worker, date):
    if worker.contractStart is empty or worker.probationEnd is empty: return false
    if worker.simpleLabor:                                         return false
    if worker.contractEnd is set and daysBetween(contractStart, contractEnd) < 365: return false
    if date < contractStart:                                       return false
    if date ≥ addMonths(contractStart, 3):                         return false
    return date ≤ probationEnd

minimumWageFor(year) := hourly of the latest MinimumWage row with row.year ≤ year
floor    := minimumWageFor(year) × (0.9 if probationApplies(worker, evaluationDate) else 1)
warning  := worker.hourlyWage < floor
evaluationDate := max(first day of the month, contractStart)

Every condition of BR-10 is a separate early return, so each can be tested on its own (TC-102): the simple-labour flag, a contract shorter than 365 days, a date three months or more after the contract start, a date after the probation end, and a missing probation end. addMonths clamps the day to the length of the target month, so a contract starting on 31 August ends its three months on 30 November. For the seed data in September 2026, Jung Hana's floor is 0.9 × 10,320 = 9,288 won and Kang Doyun's is 10,320 won; his wage of 10,000 won produces the warning.

function generatePayroll(yearMonth):                  -- services.js, inside tx()

function computePayrollRow(...):                       -- rules.js
    baseHours  := round2(Σ duration(s))
    basePay    := floor(baseHours × wage)
    holidayPay := Σ floor(h × wage) for h in holidayWeeks
    premiumPay := floor(premiumHours(shifts, regularEmployees,
                                     (contractHours, month, context)).total × wage × 0.5)
    return (baseHours, basePay, holidayPay, premiumPay,
            total = basePay + holidayPay + premiumPay,
            minWageWarning = wage < floor, estimated = any s.estimated)

4.9 User-Interface Design

The user interface was redesigned in iteration 4 (Chapter 5) after a usability review of the running application. The earlier design followed the use cases: one screen per function (inbox, approvals, weekly summary, payroll and so on), each reached from a menu. The review found that this made the user find the right screen before acting, and that the most important information — what an action does to someone's hours and pay — was on a separate screen from the action. The final design, fixed in section 2 of the final prompt and in NFR-13, is organised around the user's tasks instead. This section describes its principles, its navigation, its main screens and its visual tokens; Chapter 7 shows the screens.

4.9.1 Design principles

Eight principles apply to every screen and take precedence over the description of an individual screen.

  • Sign-in as a demo guide (UC-13).   • Worker Home. The time grid of the previous design on wide screens (hour axis from the earliest start to the latest end of the week, 44 px per hour, overlapping shifts side by side) and a day list with today expanded on phones.   • Staff, Me and Settings. Worker cards and a fixed-schedule editor with weekday chips; the worker's own profile and attendance records on Me, which no longer has an availability editor; settings in which the number of regular employees and the substitution-attendance policy each carry a sentence explaining their effect.
