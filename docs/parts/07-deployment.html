7. Deployment and User Guide

This chapter explains how ShiftSwap is deployed and how it is used. Section 7.1 describes the deployment on GitHub Pages, what happens when the application is opened for the first time, and how to reset or run it locally. Section 7.2 is a user guide organised by role and task. It follows the demonstration data of spec §10 through one complete substitution — from Lee Seoyeon's request to the owner's approval — and then through attendance, weekly summary and payroll, with a screenshot of every screen. Section 7.3 gives a short script for a live demonstration, and Section 7.4 lists common problems and their solutions.

7.1 Deployment

7.1.1 Hosting on GitHub Pages

ShiftSwap is a static web application (NFR-08), so deploying it means publishing files; there is no server program to install or start. The repository is hosted on GitHub and published with GitHub Pages [13] from the root of the main branch, with HTTPS enforced. An empty .nojekyll file in the root tells GitHub Pages to serve the files as they are, without processing them. The table below gives the addresses.

Publishing a new version consists of committing the changed files and pushing them to main; GitHub Pages rebuilds the site within a few minutes. Because all URLs inside the application are relative, the files work unchanged under the sub-path /shiftswap/app/. The deployment was checked on 2026-09-27: the application URL returned HTTP 200 with the application's index.html, and the Pages configuration reported the status "built".

7.1.2 What happens when the application is opened

  1. The browser loads app/index.html, the style sheet, vendor/sql-wasm.js and the module main.js. While the database is being prepared, the page shows "Loading the database".
  2. main.js initialises sql.js, which loads the WebAssembly file vendor/sql-wasm.wasm (about 650 KB) from the same site. No database server is contacted.
  3. If the browser's localStorage holds a saved database under shiftswap.db.v1 with the current schema, it is opened. Otherwise the schema of spec §8 is created, the demonstration data of spec §10 is inserted, and the database is saved. The demo clock is read from shiftswap.clock.v1 (default Monday 2026-09-28 09:00) and the language from shiftswap.lang.
  4. The router calls expireOverdue() and renders the sign-in screen. From now on, every change is saved to localStorage after its transaction commits.

The fonts (Pretendard and JetBrains Mono) are loaded from public font services. If they cannot be reached, the browser uses its own fonts; the application works the same, only its appearance differs. The first load therefore needs a network connection for the application files, and later work happens entirely in the browser.

7.1.3 Resetting and running locally

Reset. The header menu contains Reset demo data. After a confirmation, it deletes the saved database, recreates the demonstration data, sets the demo clock back to 2026-09-28 09:00 and returns to the sign-in screen. This restores the exact starting state of the scenarios in Section 3.8 and of this guide. Clearing the site data in the browser has the same effect.

Local run. To run the application from a copy of the repository, serve the folder with any static web server and open the app/ path, for example:

git clone https://github.com/keemlogan/shiftswap.git
cd shiftswap
python3 -m http.server 8000        # then open http://localhost:8000/app/
npm install && npm test           # optional: run the automated tests (Chapter 6)

Opening app/index.html directly from the file system does not work, because browsers do not load WebAssembly and ES modules from file:// addresses; the application then shows "The database could not be loaded. Serve the folder over http (not file://) and reload the page."

7.1.4 Browser support

The application uses only standard features: ES modules, localStorage, sessionStorage and WebAssembly. It was tested in Google Chrome on desktop (1440 px) and in Chrome's mobile emulation (360 px and 390 px). NFR-06 also names Edge, Safari and Firefox; checks in these browsers had not been recorded when this chapter was written (Section 6.7). If a browser blocks storage, for example in some private-browsing modes, the application still runs, but data is kept only until the tab is closed.

7.2 User Guide

The guide follows the demonstration data. Dalbit Café has one owner, Park Jiyoung, and four part-time workers: Lee Seoyeon, Choi Minho, Jung Hana and Kang Doyun. The demo clock starts on Monday 2026-09-28 at 09:00, and Lee Seoyeon has already asked for a substitute for her Wednesday evening shift because of a midterm exam. The screenshots were taken at 1440 px width unless stated otherwise.

7.2.1 Signing in and the header (all users)

The sign-in screen lists the five demonstration accounts. Each row shows the name, the role, and a summary: "Owner · Dalbit Café · 4 workers" for Park Jiyoung, and each worker's fixed shifts with weekly contract hours, for example "Tue, Thu 18:00–23:00, Sat 12:00–18:00 · 16 h/week" for Choi Minho. There are no passwords. Choose a row to enter the application as that person; the choice lasts until you sign out or close the tab.

The header, visible on every screen, contains from left to right: the store name, the signed-in person with the role, the Inbox button with the number of unread messages, the demo clock with +1 hour and +1 day, the language switch (English / 한국어) and the Menu with Reset demo data and Sign out. The demo clock stands in for the real time: deadlines, "today" and expiry all follow it. Change it to move the demonstration forward, for example to let a request expire (scenario S-4).

7.2.2 The weekly board (owner)

After signing in as Park Jiyoung, the owner sees the Schedule. The overview strip at the top shows the approvals waiting, the open substitute requests and the total shifts and hours of the current week; each figure links to the page where it can be acted on. Below it, the week is drawn as a time grid: seven day columns and an hour axis from 10:00 to 23:00, on which each shift is a block placed and sized by its time. Today's column, Monday 09-28, is marked. Shifts that overlap in time on the same day, such as Kang Doyun's and Choi Minho's on Saturday, are drawn side by side.

The owner's tasks on this screen are:

  • Generate a week (FR-04): go to the week with Next week and select Generate this week; the shifts are created from the fixed schedules. Generating a week twice does not duplicate shifts.
  • Add, move or delete a shift (FR-05): Add shift, or Edit on a block. A shift that has a substitute request or an attendance record cannot be deleted; change its time or worker instead.
  • Read the markers: a dashed amber outline means an open substitute request; an amber edge with stripes means a shift that was handed over (Section 7.2.14). The legend under the grid repeats this.

7.2.3 The weekly board (worker)

A worker sees the same week, but without the owner's controls and with the worker's own shifts highlighted in blue (legend "Your shift"). Workers see who works when, but no wages or phone numbers (NFR-11). On each of the worker's own future shifts without an open request, a Request substitute button opens the request form of the next section. The worker's menu contains Schedule, My requests, Inbox, Attendance and Availability; in Availability the worker enters the weekday and hours at which they could take extra shifts (UC-02), which is what makes them a candidate for other people's requests.

7.2.4 Requesting a substitute (worker)

To ask for a substitute, open My requests (or Request substitute on the board), choose the shift, optionally give a reason, and check the reply deadline. The deadline is proposed as the earlier of 24 hours from now and the shift start — here Tuesday 09-29 09:00 — and it cannot be later than the shift start. The shift list contains only the worker's own future shifts without an open request, so the Wednesday 09-30 shift, which already has a request, is not offered (BR-03). After Request substitute, the screen shows which co-workers were notified; if nobody is eligible, it says so and the owner is informed (FR-08).

The lower part lists the worker's requests with their state. The seed request for Wednesday 09-30 is "Waiting for replies", with its reply deadline, the reason "Midterm exam" and both candidates marked "No reply yet". Cancel request withdraws an open request (UC-12); the candidates are informed.

7.2.5 Answering a request (candidate)

Candidates find new requests in the Inbox, newest first; the number of unread messages appears in the header. A request message carries Accept and Decline on the message itself, so answering takes two clicks from opening the inbox (NFR-01). The first candidate to accept gets the shift, subject to the owner's approval. If another candidate has already accepted, the message shows "Already taken by <name>" instead of the buttons, and no action is needed. A decline keeps the request open for the others and informs no one.

7.2.6 Approving a swap (owner)

When a candidate accepts, the owner receives a message and the request appears under Approvals → "Accepted swaps waiting for your decision". The panel shows the effect of the swap on the week of the shift for both people: contract hours, scheduled hours, holiday-allowance eligibility and holiday hours, before and after. In the example, the swap moves five hours from Lee Seoyeon to Choi Minho, but contract hours — which decide the holiday allowance — do not change, so neither worker's eligibility changes, and the panel says so. If a swap did change a worker's eligibility, as in walkthrough S7 with the ABSENT policy, the panel would highlight that worker's row. Select Approve swap to reassign the shift, or Reject to keep it with the requester; both workers are informed either way. Open requests that nobody has accepted yet are listed below, read-only.

7.2.7 Following a request (requester)

The requester follows the request on My requests. After Choi Minho's acceptance, the status chip reads "Accepted, waiting for approval", the acceptor is named, and the other candidate's state has changed to "Closed", because the first acceptance closes the remaining invitations (BR-02). Until the owner decides, the requester can still cancel. In the form above the list, the next requestable shift is now Monday 09-28; its proposed deadline is the shift start, 18:00, because that is earlier than 24 hours from now.

7.2.8 Recording and confirming attendance (worker and owner)

After working a shift, the worker opens Attendance, enters the actual clock-in and clock-out times and selects Save record. Only shifts that have started can be recorded, so in the example the demo clock was first moved to Tuesday morning. The owner's Attendance page lists the recorded times of all workers with Confirm and Mark absent. Confirming makes the shift WORKED; marking it absent makes it ABSENT, which breaks perfect attendance for the week (BR-06). ShiftSwap does not use location data (NFR-12); attendance is self-reported and owner-confirmed.

7.2.9 Weekly summary and holiday allowance (owner)

Weekly summary shows, for each worker with shifts in the chosen week, the contract, scheduled and actual hours, whether attendance was perfect, whether the week earns the weekly holiday allowance, the holiday hours, and — when not eligible — the reason. The line above the table states the current setting for handed-over shifts ("Given-away shifts count as: not absent", the default). For a week that is not over yet, the result is a projection: shifts still scheduled do not break attendance.

7.2.10 Monthly payroll (owner)

Choose a month and select Generate draft. Each worker's row shows base hours, base pay, holiday pay, premium pay, total and flags. "Estimated" means that some shifts of the month have no confirmed attendance yet, so their scheduled hours are used (BR-11). The note above the table explains that premium pay applies only with five or more regular employees, which Dalbit Café does not have. Kang Doyun's hourly wage of 10,000 won is below the 2026 minimum of 10,320 won; his row is marked "Below minimum wage" and explains how to proceed. Jung Hana's wage is checked against the reduced probation minimum, because all probation conditions hold for her (BR-10).

Confirm payroll stays disabled until every warning has been acknowledged with Acknowledge (BR-09); the acknowledgement is saved on the row. After confirmation, the month's rows are read-only. Generating the draft again replaces only draft rows, and any acknowledgement must then be given again.

7.2.11 Workers and fixed schedules (owner)

Workers lists every worker with phone, hourly wage, contract period, weekly contract hours and status. Add worker or Edit opens a form for the personal and contract data: leave the contract end empty for an open-ended contract; the probation end is optional and used only for the 90 % minimum-wage rule; tick Simple labor for work that the law excludes from the probation reduction; clear Active when a worker leaves. Below the form, the fixed weekly shifts are edited row by row. Overlapping fixed shifts are refused with a message naming the conflict. Removing a fixed shift does not delete the shifts already generated from it.

7.2.12 Settings (owner)

Settings holds the values that the pay rules depend on. Regular employees decides whether premium pay applies (from five). The policy for shifts given away by an approved swap decides whether such a shift breaks perfect attendance; the default is that it does not. The minimum-wage table needs a row for each year; when a new minimum wage is announced, add a row for the new year. No code change is needed.

7.2.13 Using ShiftSwap on a phone

On screens narrower than 900 px the navigation moves to a tab bar at the bottom, and the weekly board becomes a list of days with their shifts in time order; the markers for open requests and handovers are the same as on the desktop. Below 720 px, tables such as the weekly summary and the payroll show each row as a card with the column name before each value, so no page needs horizontal scrolling. Inputs use a 16-pixel font, which prevents phones from zooming in when a field is selected.

7.2.14 The board after the approval (owner)

After Approve swap, the Wednesday shift belongs to Choi Minho. The board shows the handover: the new worker in bold, the original worker struck through, an amber left edge and a light amber stripe pattern. This is the only decorative element of the interface, so handed-over shifts can be found at a glance. The overview strip now shows no open requests. The weekly summaries of both workers were recomputed at the moment of approval.

7.2.15 Korean interface

The language switch in the header changes all interface text between English and Korean; the choice is remembered. Names of people and the store are data, not interface text, and stay as entered. The date and time fields are the browser's built-in controls, whose format follows the language of the operating system rather than the application.
