5. Implementation by Vibe Coding

ShiftSwap was implemented by vibe coding: its source code was generated by an AI coding assistant from natural-language prompts, and the team's work consisted of writing the specification and the prompt, running and reviewing the result, and revising the prompt until it reliably produced the system specified in Chapters 3 and 4. This chapter describes how that was done. Section 5.1 lists the development environment. Section 5.2 describes the process that was repeated in every iteration. Section 5.3 explains the structure of the final prompt, whose full text is Appendix A. Section 5.4 presents the three iterations recorded in the prompt log (Appendix B), with examples of prompt sentences before and after revision. Section 5.5 shows how the prompt maps to the code, and Section 5.6 describes the reproducibility check, in which the system was rebuilt from the final prompt in an empty folder.

5.2 The Vibe-Coding Process

The team used the same cycle for every version of the prompt. The figure below shows it; the numbered steps explain each stage and who performed it.

  1. Specify. Everything the system must do is first written into spec/spec.md: actors, use cases, requirements, business rules, states, the SQL schema, the seed data and the test groups (Appendix C). The specification is the contract. A behaviour that is not in it is not requested, and a behaviour that is in it may not be changed by the prompt.
  2. Prompt. The prompt tells the AI coding assistant how to build what the specification defines: the technology, the file layout, the names of the functions, the screens, the visual design and the conditions under which the work is finished. It refers to the specification by identifier rather than repeating it.
  3. Build. The prompt, followed by the complete specification, is given to the AI coding assistant in an empty folder. The assistant creates the files, installs sql.js, vendors its WebAssembly files, writes the tests and runs them.
  4. Verify. The team runs npm test and walks through the scenarios of Section 3.8 in the browser, including the done criteria of the prompt. Browser checks at 1440 px and 360 px are scripted with headless Chrome.
  5. Log. Whenever the specification was silent or ambiguous, the assistant was instructed to make a reasonable choice, implement it, and record it in the prompt log in the form "what was unclear → what the implementation does → suggested wording for the next version". Review findings from the team were added to the same log.
  6. Decide. For each logged item the team decided whether it belongs in the specification (it changes what the system does) or only in the prompt (it changes how the system is built), made the change, and started the next version. The rule of Section 3.11.3 applies: requirements change in the specification first.

The division of work in this cycle is deliberate. The AI coding assistant is fast at producing code but has no knowledge of the reference store or of the team's interpretation of the law, so every decision about behaviour is taken by the team and written down. Conversely, the working rule was not to fix behaviour by editing generated code by hand. When a result was wrong, the cause was traced to the prompt or the specification and corrected there, so that the next build — and any future rebuild from the final prompt — produces the corrected behaviour without depending on a manual patch.

5.3 Structure of the Final Prompt

The final prompt is version 3. It is 60 lines of Markdown and is used together with the 251-line specification, which is appended to it verbatim. The full text is reproduced in Appendix A. The table below describes its parts in order and the reason each exists.

Three principles run through the prompt. First, it is specific where variation is harmful — names, schema, keys, colours, sizes — and says nothing where variation does not matter, such as the internal structure of a screen module. Second, it refers rather than repeats: rules are cited by their BR identifier, so there is only one definition of each rule. Third, it states its own acceptance test. A prompt whose done criteria are "the walkthrough of criterion 4 works" can be checked; a prompt that asks for "a good substitute workflow" cannot.

5.4.2 Iteration 2: version 2 (build ambiguities and document review)

Version 2 folded in all 21 findings of iteration 1 and the findings of a document review, in which the proposal and the interim report were checked against the specification. The review found, among other things, that the minimum-wage acknowledgement had no place in the data model, that the recipients of a cancelled request were not defined for UC-12, and that no scenario ever changed a worker's eligibility. Twenty numbered changes were made (Section 6.9 lists them with their tests). Two changed the code: the new column Payroll.minWageAck with the service acknowledgeMinWage, and the replacement of a saved database that predates the new column. Six tests were added.

The weekly board illustrates how an imprecise prompt sentence leads to an acceptable but wrong result. Version 2 asked for "seven columns Monday–Sunday, rows are shifts ordered by start time". The assistant implemented exactly that: each day was a column of cards in time order. The result met the words but not the purpose, because the owner could not see at a glance when the café was staffed. Version 3 describes the intended picture instead: "a time grid … a vertical hour axis from the earliest shift start to the latest shift end of the displayed week, rounded to whole hours (seed: 10:00–23:00), 44 px per hour … Each shift is a block positioned and sized by its start and end time". The concrete values, including the expected axis for the seed data, made the result checkable by measuring pixel positions in the headless browser.

The verification of iteration 3 also found one defect of its own: the 32-pixel gap between groups had first been set on the outer content element, but the screens render inside an inner view element, so the header, the overview strip and the week navigation touched each other. The gap was moved to the view element, and the check was repeated.

5.6 Reproducibility Check

The course requires a final prompt that, when re-run through vibe coding, reliably reproduces a working system. A prompt that was refined on one code base may, however, depend on that code base without anyone noticing: a sentence may be understandable only to an assistant that has seen the previous version. The reproducibility check therefore rebuilds the system from nothing and tests the result with the team's test suite.

5.6.1 Method

  1. Clean start. A new session of the AI coding assistant is started with no conversation history, in an empty folder that is outside the repository. The session has no access to the repository, the existing code, the prompt log or the reports.
  2. Input. The session receives exactly what Appendix A prescribes: the text of the final prompt (version 3) followed by the complete specification spec/spec.md (Appendix C). No other instruction is given, apart from answering "continue" if the session stops before it reports completion.
  3. Build. The assistant builds the system on its own, including its own tests, and reports when it considers the done criteria of the prompt met. The number of interventions and the elapsed time are recorded.
  4. Own tests. The rebuilt system's own npm test is run and its result recorded.
  5. Team test suite. The team's test files tests/rules.test.js and tests/services.test.js are copied into the rebuilt folder, replacing the rebuilt tests, and npm test is run again. Because the prompt fixes the module paths, the exported function names and the schema, the team's tests can call the rebuilt code directly. This is the decisive measurement: it checks the rebuilt system against the same 58 or more test cases that the reference implementation passes, including the boundary values of Section 6.5, the concurrency test of Section 6.6 and the notification recipients of spec §8.
  6. Done criteria 2–4. The rebuilt application is served with a static server and opened in headless Chrome: the sign-in screen must appear without console errors (criterion 3), and the walkthrough of criterion 4 is performed. Criterion 2 (seed state and walkthrough S7) is covered by TC-001 and TC-08B of the team suite.
  7. Comparison. Any failing team test is traced to its cause and classified as (a) a genuine deviation from the specification, (b) an ambiguity in the prompt or specification that the rebuild resolved differently, or (c) a difference that the tests over-specify (for example the wording of an error message) and that does not affect a requirement. Categories (a) and (b) are defects of the prompt or specification and are reported as such.

Two limits of the method should be stated. The rebuild is a single run, and a generative assistant does not produce the same code twice, so one successful run shows that the prompt can reproduce the system, not that every run will. And the team's tests check the rules, services and data; the layout of the screens is checked only by the done criteria and the headless checks, not pixel by pixel against the reference.
