5. Implementation by Vibe Coding

ShiftSwap was implemented by vibe coding: its source code was generated by an AI coding assistant from natural-language prompts, and the team's work consisted of writing the specification and the prompt, running and reviewing the result, and revising the prompt until it reliably produced the system specified in Chapters 3 and 4. This chapter describes how that was done. Section 5.1 lists the development environment. Section 5.2 describes the process that was repeated in every iteration. Section 5.3 explains the structure of the final prompt, whose full text is Appendix A. Section 5.4 presents the five iterations recorded in the prompt log (Appendix B), with examples of prompt sentences before and after revision. Section 5.5 shows how the prompt maps to the code, and Section 5.6 describes the reproducibility check, in which the system was rebuilt from the final prompt in an empty folder.

5.2 The Vibe-Coding Process

The team used the same cycle for every version of the prompt. The figure below shows it; the numbered steps explain each stage and who performed it.

  1. Specify. Everything the system must do is first written into spec/spec.md: actors, use cases, requirements, business rules, states, the SQL schema, the seed data and the test groups. The file is not reproduced in this report; it is spec/spec.md in the repository (https://github.com/keemlogan/shiftswap/blob/main/spec/spec.md). The specification is the contract. A behaviour that is not in it is not requested, and a behaviour that is in it may not be changed by the prompt.
  2. Prompt. The prompt tells the AI coding assistant how to build what the specification defines: the technology, the file layout, the names of the functions, the screens, the visual design and the conditions under which the work is finished. It refers to the specification by identifier rather than repeating it.
  3. Build. The prompt, followed by the complete specification, is given to the AI coding assistant in an empty folder. The assistant creates the files, installs sql.js, vendors its WebAssembly files, writes the tests and runs them.
  4. Verify. The team runs npm test and walks through the scenarios of Section 3.8 in the browser, including the done criteria of the prompt. Browser checks at a desktop and a phone width are scripted with headless Chrome; from version 4 on, the script tools/check.mjs is part of the repository.
  5. Log. Whenever the specification was silent or ambiguous, the assistant was instructed to make a reasonable choice, implement it, and record it in the prompt log in the form "what was unclear → what the implementation does → suggested wording for the next version". Review findings from the team were added to the same log.
  6. Decide. For each logged item the team decided whether it belongs in the specification (it changes what the system does) or only in the prompt (it changes how the system is built), made the change, and started the next version. The rule of Section 3.11.3 applies: requirements change in the specification first.

The division of work in this cycle is deliberate. The AI coding assistant is fast at producing code but has no knowledge of the reference store or of the team's interpretation of the law, so every decision about behaviour is taken by the team and written down. Conversely, the working rule was not to fix behaviour by editing generated code by hand. When a result was wrong, the cause was traced to the prompt or the specification and corrected there, so that the next build — and any future rebuild from the final prompt — produces the corrected behaviour without depending on a manual patch.

Three principles run through the prompt. First, it is specific where variation is harmful — names, schema, keys, colours, sizes — and says nothing where variation does not matter, such as the internal structure of a screen module. Second, it refers rather than repeats: rules are cited by their BR identifier, so there is only one definition of each rule. Third, it states its own acceptance test. A prompt whose done criteria are "the walkthrough of criterion 4 works" can be checked; a prompt that asks for "a good substitute workflow" cannot.

5.4.1 Iteration 1: building from version 1

Prompt version 1 was written after the requirements and design models, as planned for Week 9 of the schedule. The first build produced a working system, and the assistant recorded 21 points at which it had to make a choice that the specification did not determine: six concerned the precision of business rules (for example, whether a week in progress can have perfect attendance, and the rounding of holiday pay), six the data and seed, three the workflow and notifications, three the technical set-up and three the user interface. The individual findings, their resolution and the tests that verify them are listed in Section 6.9.

In nearly every case the implementation had already made a sensible choice. The value of the log was that it made these choices visible, so that the team could confirm them and write them into the contract; otherwise the next build might have chosen differently, and the behaviour described in this report would not be reproducible.

5.4.2 Iteration 2: version 2 (build ambiguities and document review)

Version 2 folded in all 21 findings of iteration 1 and the findings of a document review, in which the proposal and the interim report were checked against the specification. The review found, among other things, that the minimum-wage acknowledgement had no place in the data model, that the recipients of a cancelled request were not defined for UC-12, and that no scenario ever changed a worker's eligibility. Twenty numbered changes were made (Section 6.9 lists them with their tests). Two changed the code: the new column Payroll.minWageAck with the service acknowledgeMinWage, and the replacement of a saved database that predates the new column. Six tests were added.

The table below shows how the wording changed for four representative items. The first two changed the specification, the other two the prompt.

5.4.4 Iteration 4: version 4 (UX redesign)

The fourth iteration was started after the review of the version 3 application from the point of view of a consumer-app product team. The review accepted the functions and the visual quality of version 3 but found that the interface still followed the structure of the use cases rather than the tasks of its users: a candidate had to open the inbox to find a request, the owner had to open the approvals page to see the effect of a swap, and every screen offered several actions of equal weight. Version 4 therefore rewrote section 2 of the prompt around eight UX principles and a new navigation (Section 4.9), rewrote section 3 with new design tokens, and added done criterion 5. The specification gained the usability requirement NFR-13 and a new wording of FR-20 (sign-in through a guided demo tour or the account list); the business rules, the schema and the service commands did not change. Two read queries (getWorkerHome, getOwnerHome) and the pure function menuFor(role) were added to the service layer so that the new Home screens and the role menus contain no logic of their own.

5.4.5 Iteration 5: version 5 (acceptance tests as input)

The fifth iteration followed the first reproduction run, described in Section 5.6.2. The rebuilt system worked and passed its own 54 tests, but only 13 of the team's 25 rule tests passed against it, and the team's service tests could not be loaded at all, because the rebuild had given the database factory a different name. The diagnosis was that the prompt fixed the names of modules and functions but not their signatures and return shapes, so two implementations that both satisfy the specification disagreed at the level of the interfaces. Version 5 therefore adds a section 0 to the prompt: the two test files are supplied with the prompt, must be read first and must not be changed, and they define the API. The same iteration folded two points reported by the clean session into the specification — the acceptor is re-checked for an overlapping shift at acceptance and at approval (BR-02, error ACCEPTOR_BUSY), and the three-month probation window is defined exactly (BR-10) — and fixed seven defects found by an independent code review of the reference implementation. The defects and their fixes are listed in the prompt log (Appendix B).

The seven defects — among them the missing re-check of the acceptor, attendance records that could be changed after they were final, and a 90 % probation floor computed in floating point — were fixed with twelve new regression tests: TC-01E, TC-01F, TC-01G, TC-054, TC-055, TC-072, TC-073, TC-08C, TC-106, TC-107, TC-124 and TC-125. The specification was clarified in BR-02, BR-10 and BR-12 and in FR-04, FR-05 and FR-13 (the last table of Section 6.9 lists each defect with its fix and its tests). After reproduction run 2 had started, the prompt was also given a Korean display-name map: in the Korean interface the seed people and the store are shown with their Korean names from spec §10 (for example 최민호님), while the stored names remain English.

Result of iteration 5: npm test runs 77 tests, all passing; prompt version 5 makes the two test files part of the input; and reproduction run 2 (Section 5.6.2) passed all 77 supplied tests unchanged.

5.4.6 Iteration 6: version 6 (requirements change: nobody can take the shift)

The sixth iteration was a change of the requirements, not a correction of the build. The product owner used the running version 5 and found a dead end: when no co-worker's availability matched a request, the owner received only a notice that there was no candidate and had nothing to do, and the availability slots were extra data that workers had to keep up to date. The change request, its impact analysis and the updated traceability are described in Section 3.11.4. In short, availability is removed (UC-02, FR-03 and the table Availability retired), every other active co-worker without an overlapping shift is asked (BR-01), candidates can answer can't, and a request that nobody can take ends as FAILED (BR-13, FR-22). The requester is then told to contact the owner, and the owner receives a notification whose only action is to acknowledge it.

The specification changed first, as the change procedure requires (spec §15), and prompt version 6 followed. In the prompt, the worker Home card offers 불가 ("can't") next to 수락하기; the requester's tracker shows each co-worker's answer and, for a failed request, the card "모든 동료가 대타가 불가능하다고 해요. 사장님께 연락드려 보세요."; the owner Home gains the card 대타를 못 구했어요 with only 확인했어요; the Me screen shows the worker's profile instead of an availability editor; and a new done criterion 5 requires walkthrough S8 to work in the browser, so the former criterion 5 (one primary action per screen) became criterion 6.

The prompt log lists nine changes, each with its code change and its tests. In rules.js, isEligibleCandidate lost its availability argument, and a new pure function hasNoTaker decides BR-13. In db.js, the table Availability was dropped, FAILED was added to the status check, and a database saved by version 5 is recognised as outdated and replaced by the seed. In services.js, saveAvailability and getAvailability were removed; createSubRequest and respondToRequest end a request FAILED through one shared function, and they return the new status; the two Home queries return unacknowledged REQUEST_FAILED notifications; and markNotificationsRead accepts a list of notification ids, so that acknowledging one card does not mark everything read. Because the seed request now has three candidates instead of two, several existing tests had to change their expected values.

Result of iteration 6: npm test runs 84 tests, all passing — the 77 tests of iteration 5, updated where they assumed availability, plus TC-13A to TC-13F and TC-003 (Section 6.9); and tools/check.mjs passes 128 of 128 checks at 1280 px and 360 px in Korean and English with no console errors: the sign-in screen (done criterion 3), the Korean tour walkthrough (criterion 4), five checks of walkthrough S8 (criterion 5), and the audit of 28 screen states for one filled primary button, visible reasons on disabled buttons, touch targets of at least 44 px and no horizontal scroll (criterion 6).

This exactness is the reason the traceability matrix of Section 6.8 could be derived from the code by searching for function names.

5.6 Reproducibility Check

The course requires a final prompt that, when re-run through vibe coding, reliably reproduces a working system. A prompt that was refined on one code base may, however, depend on that code base without anyone noticing: a sentence may be understandable only to an assistant that has seen the previous version. The reproducibility check therefore rebuilds the system from nothing and tests the result with the team's test suite.

5.6.1 Method

  1. Clean start. A new session of the AI coding assistant is started with no conversation history, in an empty folder that is outside the repository. The session has no access to the repository, the existing code, the prompt log or the reports.
  2. Input. The session receives exactly what Appendix A prescribes: the text of the final prompt followed by the complete specification, the specification file spec/spec.md in the repository (https://github.com/keemlogan/shiftswap/blob/main/spec/spec.md). From version 5 on, the two team test files are placed in the folder before the session starts, as the prompt prescribes. No other instruction is given, apart from answering "continue" if the session stops before it reports completion.
  3. Build. The assistant builds the system on its own, including its own tests, and reports when it considers the done criteria of the prompt met. The number of interventions and the elapsed time are recorded.
  4. Own tests. The rebuilt system's own npm test is run and its result recorded.
  5. Team test suite. The team's test files tests/rules.test.js and tests/services.test.js are run against the rebuilt code. In run 1 (prompt v3) they were copied into the rebuilt folder after the build, replacing the rebuilt tests; from run 2 (prompt v5) they are part of the input and must pass unchanged. Because the prompt fixes the module paths, the exported function names and the schema, the team's tests can call the rebuilt code directly. This is the decisive measurement: it checks the rebuilt system against the same test cases that the reference implementation passes (77 for prompt version 5, 84 for version 6), including the boundary values of Section 6.5, the concurrency test of Section 6.6 and the notification recipients of spec §8.
  6. Done criteria 2–4. The rebuilt application is served with a static server and opened in headless Chrome: the sign-in screen must appear without console errors (criterion 3), and the walkthrough of criterion 4 is performed. Criterion 2 (seed state and walkthrough S7) is covered by TC-001 and TC-08B of the team suite.
  7. Comparison. Any failing team test is traced to its cause and classified as (a) a genuine deviation from the specification, (b) an ambiguity in the prompt or specification that the rebuild resolved differently, or (c) a difference that the tests over-specify (for example the wording of an error message) and that does not affect a requirement. Categories (a) and (b) are defects of the prompt or specification and are reported as such.

Two limits of the method should be stated. Each rebuild is a single run, and a generative assistant does not produce the same code twice, so one successful run shows that the prompt can reproduce the system, not that every run will. And the team's tests check the rules, services and data; the layout of the screens is checked only by the done criteria and the headless checks, not pixel by pixel against the reference.

It showed that the prompt reproduced the behaviour but not the interfaces, and it turned that finding into a change of the prompt.
