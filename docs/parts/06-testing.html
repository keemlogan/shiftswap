6. Testing and Validation

This chapter shows how the team checked that ShiftSwap does what Chapter 3 requires. The lecture distinguishes unit testing, integration testing, system testing, acceptance testing and regression testing [6], and it defines validation as checking that the software is what the customer wants. Section 6.1 describes the test strategy and how these levels were applied. Section 6.2 gives the test environment. Section 6.3 lists every automated test of the application with its expected result, and Section 6.4 reports the result of running them together with the checks that need the shared database or a browser. Sections 6.5 and 6.6 explain the two families of tests that need the most care: boundary values of the legal rules and concurrent acceptance, which since iteration 8 can be tested across two browsers. Section 6.7 covers the non-functional requirements, Section 6.8 the traceability matrix, and Section 6.9 the defects and specification gaps found during the build iterations and how each was resolved.

Two principles guided the choice of test cases. First, the tests were derived from the requirements, not from the code: each test group corresponds to a business rule (spec §11), and each test is named with its identifier and a sentence stating the expected behaviour, for example TC-082 no holiday allowance at 14.99 h. The tests TC-01C, TC-01D, TC-134 and TC-135 were added after a traceability check in iteration 3, TC-064 to TC-066 for the Home queries of iteration 4, twelve regression tests for the defects of the independent code review in iteration 5, and TC-13A to TC-13F and TC-003 for the change request of iteration 6 (Section 6.9). The iteration 6 tests extend the group TC-13x because BR-13 has the same number; TC-13F is a rule-level test and is therefore listed with the rule tests. Iteration 7 opened the group TC-14x (TC-141 to TC-145) for BR-14, FR-23 and the seeded work history. Iteration 8 added the part-time overtime tests TC-096 to TC-09C to the group TC-09x, because they belong to BR-08, and opened the groups TC-15x (TC-151 to TC-155) for BR-15 and FR-24 and TC-16x (TC-160 to TC-16B) for the shared mode.

One further test file is not part of the application. tests/collab.test.js holds 12 tests of the collaborative-editing module of the project hub (version labels and the highlighting of changes in the report text). npm test runs it together with the application's tests, but its tests are not listed in Section 6.3 and are counted separately in Section 6.4.

6.6 Concurrency Test

NFR-04 requires that two acceptances of the same request can never both succeed. TC-051 tests this directly with the seed request: Choi Minho accepts, and then Kang Doyun accepts the same request. The expected result has four parts: the first call returns ACCEPTED; the second throws a ServiceError with the code ALREADY_TAKEN and the parameter name = 'Choi Minho', which is what the inbox displays; the request's acceptor is Minho; and the targets are ACCEPTED for Minho and CLOSED for Doyun. TC-052 checks the notifications of the same situation, and TC-063 checks the state the second candidate sees in the inbox (TAKEN, with the acceptor's name).

TC-051 calls the two acceptances one after the other on one working copy. That is faithful to SD-2 for one JavaScript thread, which executes one transaction at a time, and it verifies the design property that makes the outcome independent of timing: the service re-reads the request inside the transaction, and the update is conditional on status = 'REQUESTED', with the number of changed rows checked. Up to iteration 7 this was all that could be tested, because the client-only architecture had no shared database and therefore no truly parallel transactions. In the shared mode of iteration 8 two people on two phones can act on the same request at the same moment, and the guarantee rests on the server: it applies a change set only to the revision it was computed on, under a row lock on the store. The tests of the iteration found no defect in the rules or the services, and the shared-mode checks found none in the database. The one defect of iteration 8 was found in the layout of the sign-in screen at 360 px. The button in the notice on the shared mode (.mode-notice .btn) did not wrap its text, which made the page wider than the screen and violated NFR-02. The style rule was changed to white-space: normal in app/styles.css, and the layout check of done criterion 7 has passed for every screen state since. No test of the rules could have found this defect, since it concerns a new interface element, which confirms the value of running the layout check over every screen state after each iteration.

After the iteration, the changes since the interim state were given to two independent reviewers, one for correctness and one for security; neither found a high-severity defect, and the findings below were fixed with regression checks. (1) A request to the shared database that never received an answer blocked the gateway's queue, so the screen stayed busy until the page was reloaded; the REST transport now aborts a request after 15 seconds and reports it as offline, which returns the app to the last saved state, polling is skipped while a change is being saved, and TC-16B checks the abort. (2) Names longer than 100 characters and phone numbers longer than 40 characters passed the application's checks but were refused by the database with a general message; the services now refuse them with a message that names the field (TC-01D), and the input fields have the same limits. (3) A change set could insert a row with a key above 253, which the browser cannot represent exactly, or a payroll row that was already CONFIRMED and therefore read-only; app_commit now accepts only keys from 1 to 231−1 for new rows and the payroll trigger accepts new rows only as DRAFT, with three new REST checks. The review also noted that the limits of NFR-14 are per store and shared by all visitors, so that one visitor can use up the day's changes or resets of the demo store; this follows from the absence of accounts (spec §8, trust boundary) and was not changed, since the team can reset the store at any time through the owner connection.
